# 消息队列选型与实践：RabbitMQ、Kafka 与 6 个踩坑点

消息队列是后端解耦、削峰、异步化的核心武器，但用不好会引入"消息丢失、重复消费、顺序错乱"三座新大山。本文先讲清选型，再逐个拆解实战坑。

## 一、主流 MQ 对比

| 维度 | RabbitMQ | Kafka | RocketMQ |
|------|----------|-------|----------|
| 定位 | 通用消息中间件 | 分布式流平台 | 高吞吐消息 |
| 吞吐 | 万级/s | 百万级/s | 十万级/s |
| 消息可靠性 | 高（多级确认） | 高（副本机制） | 高 |
| 顺序性 | 单队列顺序 | 分区内顺序 | 队列内顺序 |
| 延迟 | 微秒-毫秒级 | 毫秒级 | 毫秒级 |
| 生态 | 协议丰富（AMQP） | 大数据/流处理强 | 阿里系 |
| 适用 | 业务解耦、任务调度 | 日志、流计算、大数据 | 电商交易类 |

**选型心法**：**绝大多数业务（订单、通知、任务）用 RabbitMQ 就够**；只有真正的高吞吐流场景（日志采集、埋点、数据管道）才值得上 Kafka。别为"技术时髦"选型。

## 二、MQ 解决什么问题

- **异步化**：下单后发短信/邮件，不必同步等待。
- **削峰填谷**：秒杀瞬间的流量先入队，消费者匀速处理。
- **解耦**：生产者不关心消费者是谁、有几个。

## 三、6 个高频踩坑点

## 坑 1：消息丢失（三大环节）

**消息丢失可能发生在三个环节，必须逐一防护**：

### 1. 生产者 → MQ 丢失

**场景**：生产者发消息后不等确认，网络抖动消息没到。

**修复**：确认机制 + 失败重试：

```javascript
// ✅ 等待 broker 确认
channel.confirmSelect()
channel.publish(exchange, routingKey, content)
await channel.waitForConfirms() // 未确认则抛异常，进入重试逻辑

// Kafka：acks=all（所有副本确认）才算成功
```

### 2. MQ 内部丢失

**场景**：RabbitMQ 没开持久化，broker 重启消息全丢。

**修复**：

```javascript
// ✅ 队列和消息都持久化
channel.assertQueue('q', { durable: true })       // 队列持久化
channel.publish(ex, rk, content, { persistent: true }) // 消息持久化
```

### 3. MQ → 消费者丢失

**场景**：消费者收到消息、处理前崩溃，自动 ACK 已发，消息丢失。

**修复**：**手动 ACK**——处理成功才确认：

```javascript
// ✅ 手动确认：处理完再 ack
channel.consume('q', async (msg) => {
  try {
    await process(msg)
    channel.ack(msg) // 成功后确认
  } catch (e) {
    channel.nack(msg, false, true) // 失败重投（或进死信队列）
  }
}, { noAck: false }) // 关键：关闭自动确认
```

**完整链路**：生产者确认 + broker 持久化 + 消费者手动 ACK，缺一不可。

## 坑 2：重复消费

**踩坑现场**：消费者处理成功但 ACK 丢失（网络闪断），broker 重新投递，业务被重复执行——**扣了两次款、发了两条短信**。

**原因**：MQ 的投递是"至少一次"（at-least-once），天然可能重复。

**修复**：**幂等性设计（消费端兜底）**：

```javascript
// ✅ 用唯一业务 ID 做去重（Redis / DB 唯一索引）
const bizId = msg.properties.messageId || msg.content.bizId
const ok = await redis.setnx(`consume:${bizId}`, '1', { ex: 3600 })
if (!ok) { channel.ack(msg); return } // 已处理过，直接确认跳过

await process(msg)
channel.ack(msg)
```

**核心原则**：消费逻辑必须幂等——以业务唯一键（订单号）为准，重复投递不产生副作用。

## 坑 3：消息顺序错乱

**踩坑现场**：同一条订单的"创建→支付→发货"三条消息被不同消费者并行处理，顺序乱了。

**原因**：默认多消费者并行消费，或单消费者内部多线程。

**修复**：

- RabbitMQ：**单队列单消费者**天然有序，需要并行时按 key 分队列。
- Kafka：**按 key 分区**，同一 key 的消息进同一分区，分区内有序：

```javascript
// ✅ Kafka：partition 按 key 哈希
producer.send({ topic, key: orderId, value }) // 同订单号进同一分区
```

**注意**：Kafka 只能保证**分区内**顺序，跨分区不保证。业务上需要全局限序的场景（如金融流水）要慎重设计。

## 坑 4：消息堆积

**踩坑现场**：消费速度跟不上生产速度，积压几百万条，延迟越来越大；或消费者挂了没人发现。

**排查与修复**：

1. **监控**：队列积压数、消费延迟是必配告警（RabbitMQ 管理台 / Kafka lag 监控）。
2. **消费性能**：批量消费、多消费者、异步化处理（消费回调只做入队本地任务）。
3. **消费者挂了**：重试机制 + 死信队列转移失败消息，别让一条坏消息堵住队列。

**紧急处理**：已大量积压时，临时扩容消费者数量（Kafka 要提前规划分区数，分区数 = 并行度上限）。

## 坑 5：死信队列配置缺失

**踩坑现场**：消费重试几次仍失败的消息，无限重投，卡住队列，其他消息全被拖慢。

**修复**：配置死信队列（DLX）：

```javascript
// ✅ 声明死信交换器
channel.assertExchange('dlx', 'direct', { durable: true })
channel.assertQueue('q', {
  durable: true,
  arguments: {
    'x-dead-letter-exchange': 'dlx',       // 失败消息转死信
    'x-dead-letter-routing-key': 'dead',   // 死信路由键
    'x-message-ttl': 30000,                // 消息 TTL
  },
})
// 死信队列单独消费，人工/定时处理
```

**原则**：**失败的消息不能无限重试**——重试 N 次（如 3 次）后进死信队列，人工排查或延迟补偿。

## 坑 6：事务消息 / 本地消息表

**踩坑现场**：先写数据库再发 MQ，DB 成功了 MQ 发送失败，两边不一致。

**主流方案**：

### 方案一：本地消息表（经典可靠方案）

```
1. 业务事务内：写业务表 + 写本地消息表（同一事务）
2. 定时任务扫描消息表，把"待发送"消息发 MQ
3. 收到 MQ 确认后，把消息表状态改为"已发送"
4. 消费者处理 + 幂等（配合坑 2 的去重）
```

### 方案二：事务消息（RocketMQ 支持）

```
1. 发送 half 消息（半消息，暂不可见）
2. 执行本地事务
3. 事务成功 → commit 消息可见；失败 → rollback 丢弃
4. 长时间无回执 → broker 回查本地事务状态
```

**选型**：已有 RocketMQ 用事务消息；RabbitMQ 场景用本地消息表，都依赖**消费端幂等**兜底。

## 四、实践清单

- [ ] 生产端确认机制 + 重试
- [ ] 队列/消息持久化
- [ ] 消费端手动 ACK + 失败重试 + 死信
- [ ] 消费端幂等（唯一键去重）
- [ ] 顺序性按业务确认（分区/单消费者）
- [ ] 积压、延迟监控告警

## 总结速查表

| 坑 | 解法 |
|----|------|
| 消息丢失 | 生产确认 + 持久化 + 手动 ACK |
| 重复消费 | 消费端幂等（唯一键去重） |
| 顺序错乱 | 单消费者 / 按 key 分区 |
| 消息堆积 | 批量消费 + 扩容 + 监控告警 |
| 坏消息卡队列 | 重试上限 + 死信队列 |
| DB 与 MQ 不一致 | 本地消息表 / 事务消息 |

MQ 的核心心智模型：**"至少一次投递 + 消费端幂等"是唯一真相**——别指望 MQ 帮你做到"恰好一次"，那是消费端该干的事。把幂等做好，重复消费、顺序问题、DB 一致性都能大幅缓解。
