# 向量数据库与 Embedding 实战：从原理到选型

RAG、语义搜索、推荐系统的背后，都离不开向量数据库。本文讲透 Embedding 原理、向量检索算法、主流选型对比，并给出生产级踩坑清单。

## 一、Embedding：把文字变成向量

### 什么是 Embedding

Embedding 是把任意文本映射为**固定长度的数值向量**，让语义相近的文本在向量空间里距离更近：

```
"苹果很好吃"  →  [0.12, -0.34, 0.56, ...]  (1536 维)
"我喜欢吃苹果"→  [0.11, -0.33, 0.55, ...]   ← 语义相近，距离近 ✅
"汽车在行驶"  →  [0.85, 0.21, -0.13, ...]   ← 语义无关，距离远 ✅
```

### 距离度量方式

| 度量 | 公式 | 适用 |
|------|------|------|
| 余弦相似度 | cos(θ) = A·B / (|A||B|) | 最常用，关注方向/语义 |
| 欧氏距离 | √(Σ(Aᵢ-Bᵢ)²) | 关注绝对差异 |
| 点积 | Σ(Aᵢ×Bᵢ) | 需向量已归一化时 |

**注意**：余弦相似度**越大越相似**，欧氏距离**越小越相似**，用错方向会导致检索结果完全相反。

## 二、向量检索算法

### 1. 暴力检索（Brute Force）

逐条计算查询向量与所有向量的距离，取 Top-K。

- 优点：**100% 准确**。
- 缺点：百万级数据量级下太慢（O(N)）。
- 适用：数据量 < 10 万、对延迟不敏感的场景。

### 2. ANN（近似最近邻）——生产标配

用索引结构加速检索，**牺牲少量精度换数量级的速度提升**：

| 索引类型 | 原理 | 特点 |
|---------|------|------|
| HNSW | 分层小世界图（跳表思想） | 速度/精度均衡，最流行 |
| IVF | 倒排 + 聚类（先找桶再细搜） | 内存友好 |
| PQ（乘积量化） | 向量压缩成短码 | 省内存，精度略降 |
| DiskANN | 磁盘型 ANN | 超大规模、内存受限 |

```python
# HNSW 建索引示例（faiss）
import faiss

dim = 1536
index = faiss.IndexHNSWFlat(dim, 32)  # 32 个邻居
index.add(vectors)                    # 添加全部向量
D, I = index.search(query_vec, top_k=5)  # 返回距离与索引
```

**HNSW 关键参数**：

- `M`（邻居数）：越大召回越高、内存越大，默认 16-32。
- `efConstruction`（建索引时的探索度）：越大索引质量越高、建库越慢。
- `efSearch`（查询时的探索度）：越大召回越高、查询越慢。

## 三、主流向量数据库对比

| 产品 | 类型 | 特点 | 适用 |
|------|------|------|------|
| Milvus | 分布式专用 | 大规模、云原生、支持 Filter | 百万级以上、生产级 |
| Qdrant | 专用（Rust） | 高性能、Payload 过滤强 | 中小规模、SaaS |
| Weaviate | 专用 | 内置混合检索 | 语义 + 关键词混合 |
| Chroma | 轻量嵌入式 | 本地开发友好 | 原型、小项目 |
| pgvector | PostgreSQL 扩展 | 复用现有 PG | 已有 PG 栈、量级不大 |
| Elasticsearch | 搜索引擎 | BM25 + 向量混合 | 已有 ES 生态 |

**选型心法**：

```
< 1 万条：Chroma / 内存数组即可
< 100 万条：pgvector / Qdrant / Weaviate（看现有技术栈）
> 100 万条：Milvus（分布式扩容）
已有 ES：优先 ES 的向量能力（kNN）
```

## 四、工程踩坑点

## 坑 1：Embedding 维度/模型不一致

**踩坑现场**：入库用 `text-embedding-3-small`（1536 维），查询换成 `text-embedding-3-large`（3072 维），维度对不上直接报错；即使维度一样，**不同模型的向量空间不可比**。

**修复**：**入库与查询必须用同一模型**，并在配置里固定版本；升级模型后要**全量重建索引**。

## 坑 2：余弦相似度与欧氏距离混用

**踩坑现场**：用欧氏距离的库，却按余弦相似度的大小顺序解读结果，返回的全是"距离大"的向量。

**修复**：选一个度量并全程一致；很多库默认按"距离升序返回 Top-K"，要确认排序方向。

## 坑 3：空文档/超长文档的 Embedding 异常

**踩坑现场**：空字符串或超长文本调用 Embedding API 报错或返回垃圾向量。

**修复**：

```python
def safe_embed(text):
    text = text.strip()
    if not text:
        return None  # 跳过，不入库
    if len(text) > MAX_LEN:  # 超长先切分再分别编码（或截断）
        text = text[:MAX_LEN]
    return embed_fn(text)
```

## 坑 4：索引参数没调，召回率感人

**踩坑现场**：HNSW 用默认参数，百万级数据召回率只有 70%，检索不到正确结果。

**修复**：用**评测集量化召回率**，调 `efSearch`/`M` 直到达标：

```
评测流程：准备 100 个 (query, 正确答案) 对
  → 暴力检索算"标准 Top-K"
  → ANN 检索对比，算 Recall@K
  → 调参直到 Recall@K ≥ 0.95（在可接受的延迟内）
```

## 坑 5：数据更新后索引不一致

**踩坑现场**：删了文档，向量库里旧向量还在；改文档后新旧向量并存。

**修复**：

- 每条向量带**元数据**（文档 id、版本 hash、更新时间）。
- 更新流程：先按文档 id 删除旧向量 → 再写入新向量。
- 定期全量重建 + 索引段合并。

## 坑 6：过滤条件与向量检索脱节

**踩坑现场**：想"只搜 2026 年的文档"，但过滤条件在向量检索之后才应用，Top-K 里全是旧文档。

**修复**：把过滤条件**下推到向量数据库**（pre-filter），而不是先检索再过滤：

```python
# ❌ 先检索再过滤：Top-K 可能全被滤掉
# ✅ 下推过滤：数据库先按条件筛再向量检索
collection.query(
    query_embeddings=[vec],
    n_results=5,
    where={"year": 2026},          # Chroma 过滤语法
)
```

## 坑 7：忽略向量归一化

**踩坑现场**：用点积做度量，但向量没归一化，长度不同的向量结果被"长度"干扰。

**修复**：点积场景先归一化（L2 norm），或直接改余弦相似度。faiss 里 `IndexFlatIP`（内积）要求预先归一化。

## 坑 8：多租户/多数据集隔离缺失

**踩坑现场**：多个项目共用一个 collection，检索互相污染。

**修复**：

- 每个租户独立 collection，或用**租户 id 过滤字段**（注意坑 6，过滤要下推）。
- 命名规范：`{租户}_{用途}`，避免命名冲突。

## 五、生产链路清单

```
1. Embedding 模型固定版本，入库/查询一致
2. 度量方式统一（推荐余弦）
3. 空/超长文本防御
4. ANN 索引参数用评测集调优
5. 元数据携带（id/版本/时间/来源）
6. 更新走"删旧写新"，定期重建
7. 过滤下推到向量库
8. 监控：召回率、查询延迟、索引规模
```

## 总结速查表

| 问题 | 解法 |
|------|------|
| 维度不一致 | 固定同一 Embedding 模型 |
| 度量混乱 | 统一余弦，确认排序方向 |
| 空/长文本 | 防御处理，切分/跳过 |
| 召回率低 | 评测集调 HNSW 参数 |
| 数据过时 | 删旧写新 + 定期重建 |
| 过滤失效 | 过滤下推到向量库 |
| 点积异常 | L2 归一化 |
| 多租户污染 | 独立 collection / 过滤字段 |

向量数据库的核心心智模型：**它是"语义搜索引擎"，不是"数据库"**——价值在于按语义找内容，而不是存数据。把 Embedding 一致性、索引参数、元数据治理这三件事做好，向量检索就能稳定服务生产。
