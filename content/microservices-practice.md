# 微服务架构实践：服务拆分、注册发现与 7 个踩坑点

微服务不是银弹——拆分不对、治理缺失，微服务会把一个简单的单体问题放大成分布式难题。本文讲清演进路线、核心组件与高频踩坑。

## 一、什么时候该上微服务

**先问三个问题**：

1. 团队是否大于 10 人且多个小组并行开发？
2. 是否真的需要独立扩缩容（不同服务的负载差异大）？
3. 是否有足够的运维能力（监控、链路、容器化）？

**如果答案都是否，单体 + 模块化更合适**。微服务解决的是"组织与扩展"问题，不是"代码整洁"问题。**规模没到就上微服务，等于用分布式复杂度换想象的收益**。

## 二、服务拆分的正确姿势

### 按业务域拆（DDD 思想）

```
用户服务 user-service
订单服务 order-service
支付服务 payment-service
商品服务 product-service
```

### 拆分原则

- **高内聚低耦合**：一起变更的业务放一个服务。
- **按数据边界拆**：一个服务持有自己的数据，**禁止跨服务直接查库**。
- **先按团队边界拆**：一个服务对应一个团队长期维护。

**坑 1：按"技术层"拆**——把 controller / service / dao 各拆成一个服务，这是最常见的错误拆分方式，会导致无意义的网络调用和事务地狱。

## 三、核心组件与选型

| 组件 | 作用 | 主流选型 |
|------|------|---------|
| 注册中心 | 服务发现 | Nacos / Consul / Eureka |
| 配置中心 | 配置管理 | Nacos / Apollo |
| 网关 | 统一入口、路由、鉴权 | Spring Cloud Gateway / Kong |
| 服务调用 | RPC | OpenFeign / Dubbo |
| 熔断限流 | 保护依赖 | Resilience4j / Sentinel |
| 链路追踪 | 排障 | SkyWalking / Zipkin |
| 消息 | 异步解耦 | RabbitMQ / Kafka |

## 四、7 个高频踩坑点

## 坑 1：注册中心节点挂了，服务全崩

**踩坑现场**：注册中心（Nacos/Consul）宕机，所有服务互相找不到。

**原因**：服务**强依赖**注册中心，或注册中心只有单节点。

**修复**：

- 注册中心**集群部署**（至少 3 节点）。
- 服务端**本地缓存 + 服务端主动发现**：即使注册中心不可用，已注册的服务也能靠本地缓存继续通信。
- 调用失败要有重试 + 熔断兜底。

## 坑 2：服务间直接调数据库（数据边界被打破）

**踩坑现场**：order-service 直接查 user 表，"为了省一次 RPC"，结果两边都改库，数据一致性崩溃。

**修复**：**数据按服务归属**，跨服务数据只能通过 API 获取；需要聚合时用**API 网关聚合**或 **CQRS/物化视图**。

**坑**：如果非要共享库，那不如别拆服务——共享库是微服务最大的伪需求来源。

## 坑 3：分布式事务：跨服务一致性

**踩坑现场**：下单要扣库存（库存服务）+ 扣余额（钱包服务），一个成功一个失败，数据不一致。

**主流方案**：

| 方案 | 特点 | 适用 |
|------|------|------|
| 本地消息表 | 可靠、实现简单 | 最终一致 |
| 事务消息（RocketMQ） | 自带半消息 | 最终一致 |
| TCC（Try-Confirm-Cancel） | 强一致、实现复杂 | 高价值场景 |
| SAGA | 补偿式 | 长流程 |

**原则**：**能不跨服务事务就不跨**——通过业务设计避免（如把"扣库存+扣余额"合并为同一个服务的本地事务），无法避免时选**最终一致 + 补偿**，TCC 只用于核心高价值场景。

**坑**：试图用"分布式事务"包住所有跨服务操作，最后锁冲突和复杂度反噬。**优先用业务手段消除分布式事务**。

## 坑 4：服务间调用超时设置不当

**踩坑现场**：A 调 B，B 调 C，C 挂了，A 的线程全部挂在等待上，线程池耗尽，**雪崩**。

**修复**：**每层调用必须设超时 + 熔断**：

```yaml
# OpenFeign 超时配置
feign:
  client:
    config:
      default:
        connectTimeout: 2000
        readTimeout: 3000

# 熔断（Resilience4j）
resilience4j:
  circuitbreaker:
    instances:
      order-service:
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
```

**原则**：**超时时间自内向外递增**（内层服务超时 < 外层服务超时），否则外层超时了内层还在跑，资源白白消耗。

## 坑 5：网关单点

**踩坑现场**：网关是唯一入口，网关挂了全站不可用。

**修复**：网关**多实例部署** + 前置 LB（Nginx/云负载均衡）；网关本身要**无状态**，方便水平扩展；必要时做**多级网关**（边缘网关 + 业务网关）。

## 坑 6：链路排障靠翻日志

**踩坑现场**：一个请求跨 5 个服务，出问题后每个服务各查各的日志，对不上号。

**修复**：**全链路追踪**：

```yaml
# 每个服务接入 traceId 透传（Spring Cloud Sleuth / OpenTelemetry）
# 日志统一格式包含 traceId
{"traceId": "8f2a1c...", "service": "order-service", "level": "ERROR", "msg": "..."}
```

**原则**：**traceId 从网关入口生成，全链路透传**（HTTP Header `X-Trace-Id` / MQ 消息属性），日志、告警、监控全部按 traceId 关联。没有链路追踪的微服务等于裸奔排障。

## 坑 7：配置散落各服务

**踩坑现场**：改个数据库连接串要登录 5 台机器手动改；不同环境配置漂移，测试环境好了生产挂了。

**修复**：**配置中心统一管理**（Nacos/Apollo）：

- 配置**分环境**（dev/test/prod 隔离）。
- 敏感配置加密存储。
- 配置变更支持**灰度发布**和**回滚**。

## 五、微服务实践路线图

```
第一步：单体模块化（按业务域拆模块，保留单体部署）
第二步：拆第一个服务（选业务边界清晰、独立扩展价值的）
第三步：搭基础设施（注册中心 + 配置中心 + 网关 + 日志/监控）
第四步：逐步拆解（一次拆一个，每拆一个配套熔断/超时/链路）
第五步：容器化 + CI/CD 自动化
```

**关键**：**不要大爆炸式拆分**。一次拆一个服务，每步保持系统可用，配合监控验证。

## 总结速查表

| 坑 | 解法 |
|----|------|
| 注册中心单点 | 集群 + 本地缓存兜底 |
| 跨服务查库 | 数据按服务归属，API 获取 |
| 跨服务事务 | 业务设计规避 / 最终一致 + 补偿 |
| 调用无超时 | 每层超时 + 熔断，超时由内向外递增 |
| 网关单点 | 多实例 + 前置 LB |
| 排障靠翻日志 | 全链路 traceId 透传 |
| 配置散落 | 配置中心统一管理 |

微服务的核心心法：**微服务是"组织架构的映射"，不是"技术的炫技"**——拆分跟着团队和业务走，治理跟着稳定性走。每引入一个分布式组件，都要问一句：它解决的实际问题是什么？没有明确答案的组件，就是未来的负债。
